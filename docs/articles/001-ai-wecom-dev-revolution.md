## 一个真实故事

上个月，一个做教培的朋友打电话来，声音很疲惫。

他的团队花了两个月用 AI 写了一套企微 SCRM——"AI 很猛啊，Cursor 几分钟就写完一个模块"。结果上线第一天就炸了。新客户扫码加好友后，一半人收不到欢迎语。销售群炸锅，教务投诉，老板开会问责。

最后排查了两天才发现：**企微的 WelcomeCode 有 20 秒有效期**。他们的异步消息队列在高峰期延迟超 20 秒，欢迎语直接失效。

AI 不知道这个限制。官方文档里也没写明白。

这不是个案。**在企微开发这个领域，AI 正在以一种全新的方式制造混乱。**

---

## AI 写代码很强，但在企微面前很脆弱

2026 年了，没人怀疑 AI 的代码能力。Cursor、Claude Code、Copilot……一行提示词就能生成完整的函数，配合 MCP 工具链甚至可以自动联调。

但企微 API 是一个特殊战场。

它的特殊在于：大模型的训练数据里，企微 API 文档极度稀缺，而**官方文档和实际行为之间存在大量未记录的 gap**。

AI 拿着残缺的记忆在写代码，结果可想而知：

- **凭空编造接口** — 问 AI 怎么给客户打标签，它会自信地写出 `/cgi-bin/externalcontact/addContactTag`。这个接口不存在。
- **搞混关键字段** — `follow_user` 和 `follow_info` 看起来很像，语义完全不同。一个是跟进成员列表，一个是关注信息对象。用错了，你的客户画像就全乱了。
- **违背协议习惯** — linkedcorp 系列接口全部是 POST，包括查询操作。AI 按直觉用 GET，服务器返回 404，你以为是权限问题，排查一天。
- **忽略生产暗知识** — access_token 文档写有效期 7200 秒，但实际生产中必须 7000 秒就刷新，否则在那 200 秒的窗口里，你的所有 API 调用都可能失败。

这不是 AI 的能力问题，**是 AI 缺少结构化的知识输入**。

---

## 一个更深层的问题：AI 能写代码，但写不出系统

我们需要拉高一层来看这件事。

很多人有一个直觉：既然 AI 能写代码，那我让它把整个 SCRM 系统写出来不就行了？

**这个直觉是错的。**

AI 擅长生成「代码片段」——一个函数、一个组件、一段 API 调用。但从「代码片段」到「可商用的系统」，中间隔着一条巨大的鸿沟：

| 你真正需要做的事 | 典型耗时 | AI 能替代吗？ |
|:------------|:------:|:--------:|
| 业务需求分析与架构设计 | 1-2 月 | 不能 |
| 10+ 模块间的联动逻辑 | 2-3 月 | 不能 |
| 企微 API 踩坑与适配 | 1-2 月 | 极少部分 |
| 安全审计与合规 | 1 月 | 不能 |
| 生产环境压测与调优 | 1-2 月 | 不能 |
| 部署与运维体系 | 1 月 | 不能 |
| **合计** | **6-12 个月** | — |

举个例子，一条最基本的企微 SCRM 业务链：

```
客户扫码 → 自动分配员工 → 打标签 → 触发 SOP 欢迎语
  → 3天后推送产品链接 → 7天后推送优惠券
  → 客户回复后 AI 识别意向 → 通知销售跟进
```

这条链路涉及 5 个业务模块、12 个 API 调用、3 种异步策略。AI 能写其中任何一段代码——但无法设计这条完整的业务链，因为**这是商业经验的沉淀，不是代码逻辑**。

所以问题的本质是：

> **AI 是一台强大的发动机，但你需要给它一条建好的公路。**
>
> 公路 = 经过验证的知识体系 + 经过打磨的系统基座。

## 解法的前半段：给 AI 装上「企微大脑」

这正是 **Open WeCom Skills** 在做的事情。

Open WeCom Skills 不是又一份 API 文档的搬运。它是一套**为 AI 深度优化的企微结构化知识体系**，来源于真实的大规模生产实践——具体来说，是源雀团队六年服务 500+ 企业过程中沉淀下来的一线经验。

### 三层知识架构

**① 精确的 API 定义层**

每个接口的请求方式、参数格式、响应结构、频率限制，全部以 AI 可消费的结构化文本编写。AI 不再需要"凭记忆猜"，而是精确查阅。

```
// AI 查阅 SKILL 后的行为变化
❌ 凭记忆："大概是 /addContactTag 吧"
✅ 查 SKILL："POST /cgi-bin/externalcontact/mark_tag，
             参数 userid + external_userid + add_tag[]"
```

**② 踩坑指南层（Gotcha Guide）**

把 500+ 企业验证过的「坑」提前植入 AI 的知识上下文，让 AI 在你踩坑之前就主动预警：

- WelcomeCode 有效期 20 秒，必须同步处理
- linkedcorp 全部 POST，包括查询接口
- access_token 建议 7000 秒刷新，而非文档写的 7200 秒
- 会话存档需 RSA 私钥本地解密，不能直接读明文

这些信息，绝大多数不在官方文档里，只存在于踩过坑的工程师脑子里。

**③ 五语言即用代码模板**

Python / TypeScript / Go / Java / PHP 五种语言的代码模板，AI 可以直接修改使用，跳过从零编写的过程。

### 效果对比

**没有 SKILL 时**：

```
你：帮我写一个给客户打标签的企微 API 调用

AI：好的，我来调用 /cgi-bin/externalcontact/addContactTag...
    （编造了一个不存在的接口名）

你：接口名不对。

AI：抱歉，让我查一下... 应该是 /cgi-bin/tag/addCorpTag...
    （又编了一个）

# 你不得不自己翻文档，然后手动纠正 AI
```

**有 SKILL 时**：

```
你：帮我写一个给客户打标签的企微 API 调用

AI：[自动查阅 wecom-crm-tag SKILL]
    接口：POST /cgi-bin/externalcontact/mark_tag
    参数：userid（员工）、external_userid（客户）、
         add_tag（标签ID数组）、remove_tag（移除数组）

    注意事项：
    - 标签 ID 需先通过 get_corp_tag_list 获取
    - 每次只能标记 1 个客户，批量场景需循环调用
    - 标签组上限 100 个，每组标签上限 100 个

# AI 一次到位，你直接进入业务开发
```

## 解法的后半段：站在验证过的系统上起跑

知识体系解决了 AI "知道什么"的问题。但要真正做出一个可跑的企微 SCRM 系统，你还需要一个**经过验证的基座**。

这就是为什么在 AI 时代，源码反而比过去更值钱了。

> **不是因为 AI 写不了代码，而是因为你的竞争对手等不了 6 个月。**

AI 是加速器，但加速器需要跑道。

- **没有跑道的加速器** — AI 帮你写了一堆代码片段，但互相不兼容，模块之间的联动需要你手动设计。6 个月后也许能跑。
- **有跑道的加速器** — 你拿到一套经过 500+ 企业打磨的完整系统源码，用 AI 在上面做二次开发和行业定制。第一周就能部署。

两种路径的差距，不是效率差距，是**确定性差距**。

**当知识体系 + 系统基座同时存在时，组合效应才真正爆发：**

```
源码（基座） → 10大模块、550+ 功能点直接可用
    +
Open WeCom Skills（知识） → AI 精通全部 API，二次开发不踩坑
    +
AI 工具（引擎） → 在源码基础上快速定制行业功能
    =
上线时间：从 6-12 个月 → 1-2 周
```

## 接入方式：一行配置

Open WeCom Skills 通过 MCP（Model Context Protocol）交付。在你的 AI 工具中添加一行配置：

```json
{
  "mcpServers": {
    "omnisockit": {
      "command": "npx",
      "args": ["@omnisockit/mcp-server"]
    }
  }
}
```

零克隆、零配置。AI 会按需读取 SKILL，在你开发企微功能时自动获取精确的 API 知识。

兼容所有主流 AI 工具：Claude Desktop / Claude Code / Cursor / Windsurf / VS Code + Copilot / Trae / Antigravity / Cline / Roo Code / Kilo Code 等。

## 安全性

MCP Server 的设计原则是**纯知识交付，零副作用**：

- 不调用任何外部 API
- 不需要你的 corpid、secret、access_token
- 不收集任何数据
- 纯本地运行，通过 stdio 与 AI 工具通信
- 开源可审计，`npm pack` 可检查全部源码
